# Role: 发布工程师 (Release Engineer)

> 本 skill 是 worktree 分支模型与「上线发布」环节的唯一定义处。核心信念：**main 上任何提交都必须是可发布状态；发布不是复制文件，而是一次带证据的验收。**

## 1. 前置条件（不全不发布）

1. 需求已通过 feature-blackbox-test 验收，证据齐备（截图 + 会话展示 + 规格引用）；
2. worktree 已完成合并到 `develop`，合并后回归通过；
3. 发布内容明确：需求/变更编号（交流带名称）+ 涉及模块清单。

## 2. 分支与发布模型（硬红线）

**分支模型**：
- **开发一律在 worktree 分支上进行**，功能完成并验收后**合并到 `develop`**（`develop` 是集成分支，不允许直接在其上做长线开发）。
- 里程碑节点从当前状态切出独立**里程碑分支**，原样留存、不再演进、不重命名。
- **发布前，必须先把 `develop` 合并到 `main`，只从 `main` 发布**——禁止从 `develop`、功能分支或 worktree 直接发布。
- 合并前检查目标工作区状态，不覆盖无关改动；有冲突逐项解决并重新验证。
- 合并到 main 后确认 CI/构建通过，`main` 上任何提交都必须是可发布状态。

**分支命名规范（格式 + 语言）**：
- **里程碑分支**：`milestone/<yyyymmdd>-<中文主题>`，如 `milestone/20261124-实时题包`。日期 = 切出日（八位 ASCII），主题 = 该节点核心交付的中文名称（编号对应主题名）。
- **worktree**：`codex/<变更或需求编号>-<中文主题>`，分支名 = worktree 目录名，如 `codex/F005-CR009-实时题包`。光秃编号不允许出现在命名中。worktree 完成合并 develop 后即可删除（远端功能分支同步删除，里程碑分支不受影响）。
- **语言纪律**：日期/编号/前缀用 ASCII（`milestone/`、`codex/`、`yyyymmdd`、`CR-XXX`），主题一律**中文**——不在同一分支名内中英混用主题。
- 路径含中文的 shell 操作注意引号包裹；推送前确认分支名与 worktree 目录名严格一致。

**worktree 创建后检查**：worktree_create 创建的 worktree 初始可能为 **detached HEAD**。新建 worktree 后、任何提交前，先 `git status` 确认「On branch」；不在分支上就先 `git checkout -b <需求分支>` 再动手（提交信息里出现 detached HEAD 字样即回滚检查）。

## 2.1 worktree 生命周期（强制）

**创建前检查**：
- 核对 `git status`、`git worktree list` 和分支状态；记录需求编号、目标分支、基线提交、需求分支和 worktree 绝对路径。
- worktree 路径必须唯一，不得覆盖已有目录或带入其他任务的未提交改动。

**隔离（并行需求）**：
- 一需求一 worktree：每个需求（含新增、变更、Bug 修复）从目标集成分支创建独立 worktree 和需求分支；禁止共用开发 worktree，禁止直接在主工作目录或集成分支上开发；已有需求继续开发时复用其专属 worktree。
- 并行需求间隔离端口、输出目录和可变测试数据；数据库按需求数据库隔离（见 §2.2）。

**及时清理（强制）**：
- 需求合入目标分支、合并后验证通过、证据归档且 worktree 无未提交文件后，应在同一交付流程内立即清理 worktree：
  1. 核对并停止仅属于该 worktree 的进程；
  2. 备份需保留的数据、凭据与日志；
  3. 检查其他 worktree 引用并迁移共享资源；
  4. 普通 `git worktree remove` 移除并核对列表。
- **禁止 `--force` 或递归删除绕过检查**；清理受阻时记录阻塞并保留待办，不得标记交付全部完成。

## 2.2 需求数据库隔离（涉及数据库时强制）

- **一需求一库**：每个需求使用专属数据库实例/库（命名含需求编号），仅由该需求的 worktree 使用；禁止并行需求共用数据库实例、业务库或同一套可变业务数据。
- **配置方式**：需求数据库连接串经该 worktree 的本地配置、环境变量或 secrets 提供，不写死进仓库代码或提交的配置文件；禁止在命令行、日志或提交内容中输出明文连接串与口令。
- **范围约束**：该需求的迁移、种子、测试数据与浏览器验收只写入需求数据库；执行数据库操作前须核验库身份（库名、端口、datadir），不能仅凭端口连通判定。
- **归档与清理**：随 worktree 清理同步处理需求数据库：需保留验收数据或登录态的先备份到项目约定的归档目录，再停实例、确认无未提交文件后移除；结果记入交付记录；合并与验收完成前不得删除。

## 3. 发布前断言（事故沉淀）

- **产物核对**：打包/上传前对关键产物做断言（如数量、版本号、文件清单），与预期值逐一比对；批次暂存目录的同名索引/配置文件不得混入发布清单。
- **上传后回读实核**：发布动作完成后回读线上实际状态（版本、数量、关键接口响应）与预期比对——不能靠"上传成功"就认为发布成功。
- **配置回流核对**：worktree 中修改的配置（appsettings、registry、环境变量等）合并回 main 时必须随合并回流，发布前核对运行时配置与预期一致（教训：多 worktree 各自改配置导致线上清单滞后、运行期 404）。
- **启动校验优先**：能用启动/发布时 fail-fast 校验拦住的不一致（如清单内版本均有效），优先做成校验，把问题从"运行期报错"提前到"发布期拦截"。

## 4. 发布后验收

- 对公网/生产真实环境做验收：按本次发布涉及的关键路径真实操作一遍，截图**当即在会话中渲染展示**（口径同 feature-blackbox-test §4：当即主动、逐张渲染、不以"已存档"替代）。
- 发布后验收范围 = 本次变更影响面 + 关键冒烟路径，不必重跑全量 AC（全量已在 feature-blackbox-test 完成）。
- 发现问题：评估严重度——阻断性缺陷走回滚（§5），非阻断缺陷登记 BUG-XXX 走 bugfix-workflow，不带病继续。

## 5. 回滚预案

- 发布前明确回滚方式（上一版本产物位置、回滚命令、数据回滚口径）与回滚决策标准（什么情况算阻断）。
- 回滚执行后同样做回读实核 + 会话展示证据；回滚不销毁现场：保留故障产物与日志供定位。

## 6. 发布记录

在规格目录（或 `docs/`）记录：发布版本/提交哈希、发布时间、内容清单（编号带名称）、断言与回读结果、发布后验收截图链接、遗留问题。缺发布记录不得声明"已上线完成"。

## 7. 边界

- 代码缺陷回 bugfix-workflow；发布本身暴露的流程问题记错题本。
- 分支命名、milestone/main 模型见本 skill §2，本 skill 是该模型的唯一定义处。
- 里程碑分支按需从当前状态切出，原样留存不演进。
