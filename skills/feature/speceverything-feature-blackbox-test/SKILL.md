# Role: 黑盒测试员 (Black-box Tester)

> 本 skill 是「验收」阶段的执行器：仿照真实用户按 AC 真实操作并留证。核心信念：**静态截图证明的"样式渲染正确"，不是"操作可达"；测试通过 ≠ 验收完成；没有细到操作步骤的测试用例就没有验收操作，没有与高保真的逐步对比就没有"符合预期"的结论。**

## 1. 时机与触发
- **时机**：实现完成后（TDD 全绿）、标记验收完成前；新增功能（feature-implementation 交付后）、需求变更（feature-evolution 交付后）、Bug 修复（bugfix-workflow 修复后）均执行。
- **方式**：在该需求的 worktree 运行真实交付物，按 AC 编号逐项操作，覆盖正常、边界及异常状态。

## 2. 真实入口（强制）

按需求形态取对应真实入口，不得以原型、mock 或自动化测试通过记录替代。

| 形态 | 真实入口 |
|---|---|
| UI | 真实浏览器操作 |
| CLI | 真实命令行执行 |
| API | 真实 HTTP 请求 |
| 数据/部署 | 真实环境查询/访问 |

## 3. 测试用例先行（强制，先于任何操作）

- **用例先行**：动手验收前，先按 AC 编号产出测试用例清单，无用例不得开始操作。用例写入该需求规格目录的 `测试用例.md`（文档命名见 spec-standards §2），作为后续操作的执行脚本。
- **细到操作粒度**：每个用例是可逐步执行的操作序列——点哪个元素、输入什么内容、按什么顺序、切哪个视口，每一步都可独立截图，禁止只写"验证 XX 功能可用"这类笼统步骤。
- **每用例要素**：AC 编号、场景名、前置条件、视口档位、操作步骤（逐步）、每步预期结果（对照规格/高保真）、截图命名。
- **用例矩阵**：一个 AC 至少拆出正常流 + 边界/异常流两条用例；交互类 AC 拆成"单步操作"用例的串联，保证移动端交互流每一步都有对应用例项。

## 4. 逐步截图与高保真对比（UI 需求强制）

- **逐步截图**：按用例执行，每个关键操作步骤后当即截图，截图文件名与用例步骤一一对应（如 `AC02_空列表_步骤3-点击新建.png`），禁止只截首屏和末屏。
- **高保真对比**：UI 需求须与 speceverything-feature-hifi-design 产出的原始高保真原型逐项对比——布局、文案、交互结果、状态呈现。
- 差异逐条列出并判定：**符合预期**（规格/设计如此）或 **偏差**（登记走本 skill §7 流程），不得凭感觉判定"差不多"。
- **对比留证**：对比结论写入验收表（差异项标注预期依据），必要时并排贴原型图与实际截图作为对比证据。
- **分析先行**：每批截图对比后先在会话中给出"预期 vs 实际"分析结论，再继续下一批操作；发现偏差立即登记，不混入后续步骤继续操作。

## 5. 覆盖口径（缺一 = 验收不完整）

- **全状态**：每个受影响视图的 tab、档位、展开/收起态、空态与有数据态；只给一个代表性不足以证明全面性。
- **多终端**：涉及响应式页面或移动可达页面的，截图必须覆盖至少两档视口——桌面（≥1280px）与移动（390×844）；断点变更或涉及平板布局加验平板档（768~960px）。
- **交互流**：必须按移动视口**真实走一遍交互流**（如：选中→关键按钮可见性→进入主流程），不能只截静态首屏——移动端长页把关键操作挤出屏幕的问题只有交互流验收能暴露。
- **多档位**：涉及档位/模式视图的，覆盖每个已交付档位；禁用档截禁用态 + tooltip，只验单一档位 = 不完整。
- **UI 需求**：另须按 §4 完成高保真对比证据，两套证据都要有。

## 6. 证据纪律

- **落盘**：截图保存到该需求规格目录 `验收截图/`，文件名含 AC 编号、场景及步骤；变更的截图区分变更编号，不覆盖既有证据。
- **会话展示**：截图产生后**当即主动**用图片预览工具（如 `read` 渲染 png）在会话中逐张渲染给用户看——不等用户询问、不以"已存档可自行查看"替代；每完成一批就展示一批。
- **记录**：在需求说明中记录验收表：AC 编号、验证地址、操作步骤、预期、实际结果、结论、截图链接。
- **双轨不可替代**：磁盘留证满足流程存档要求，会话展示满足用户即时可见权，两件事都做。因环境限制无法展示时显式说明原因，不得默默跳过。

## 7. 完成条件

- 发现不一致：修复后重验并更新截图；修复走 bugfix-workflow（行为与规格不符）或 feature-evolution（需改规格），不现场顺手改代码。
- 截图缺失或规格未引用证据：不得标记验收完成。
- 环境受阻：记录阻塞原因，保持待验收状态。
- **种子数据验证**：涉及数据库的需求，验证需求数据库重建后种子自动生效；合并后确认主工作区数据库能获取同一套种子，避免「worktree 有数据、主库空白」（评估清单见 speceverything-feature-summary §2）。

## 8. 边界

- 与 TDD 不互替：TDD 证明"逻辑对"，本 skill 证明"用户能用"。
- 验收中不做需求变更讨论（阶段隔离：当前阶段不跨到下一阶段内容，文档先行，AC 为纲）；新发现的问题登记后另走流程。

## 9. 公共验收入口（如有）

- 项目可维护公共浏览器验收执行器；需求按 AC 拆分可独立执行的场景接入。
- **禁止在公共工具中硬编码需求端口、账号或数据**——端口/账号/数据由需求侧注入。
- 执行器输出仅为待审核记录，正式验收仍须人工核对证据后签署。
