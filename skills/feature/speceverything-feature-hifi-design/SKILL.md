# Role: 高保真设计师 (Hi-Fi Design)

> 本 skill 是「UI 设计稿」阶段的执行器：把已确认的需求与 AC 转成用户可评审、可点头的高保真设计。核心信念：**写第一行实现代码之前，会话里必须已有用户点过头的设计图。**

## 1. 时机与门禁
- **时机**：需求文档与 AC 确认后、技术方案编写前，是独立步骤；设计定稿后才写技术方案。
- **门禁**：用户未确认的高保真设计，技术设计与实现一律不开工；会话内用户确认记录 = 需求依据，后续登记编号（CR-XXX/F00X）时须引用该确认。
- **变更触发**：UI 交互变化时，先更新设计稿与规格（经 speceverything-feature-evolution 登记变更），再改实现，确保设计稿、AC 与交付界面一致。
## 2. 产出物

**设计过程工具（按需调用，一律为中间态）**：探索期可使用 `.agents/skills/` 下的设计工具——create-canvas / component-canvas 在画布上并列探索布局变体与既有组件变体（服务于「复用既有」的先检索纪律）；create-design-md 仅在「有既有代码证据 + 用户同意」时从代码反向沉淀 `specs/design/DESIGN.md` 契约，绿地项目禁止伪造契约——定稿原型即创世契约，落定后回填。过程产物不替代本节强制产出物，定稿门禁不变。

### 2.1 HTML 高保真原型
- **位置**：该需求规格目录 `UI设计图`；在需求说明（及变更文档）中链接引用。
- **内容要求**：
  - 关联需求 AC 编号；
  - 覆盖主要界面与交互流程，包含**正常、空数据、加载、错误、禁用**五类状态；
  - 可交互（页面间跳转、关键交互可达），不接真实业务、数据库或设备；
  - **多端适配**：目标终端以需求说明「目标终端」声明为准；未声明的默认桌面（≥1280px）+ 移动（390×844）两档视口，与 feature-blackbox-test §5 验收口径一致。原型在各目标视口下展示布局适配（断点行为、无横向溢出、文字不截断、关键操作不挤出屏幕）；需求声明与默认不符的档位不做，声明缺失且未向用户确认即只出单端属流程违规；
  - 对齐项目设计契约（如 `specs/design/DESIGN.md`），复用既有 CSS token、组件类与布局模式——设计不得另起炉灶硬编码（先搜现有实现，见 feature-implementation「动手前的两条纪律」）。
### 2.2 区域标注图（每次出图强制）
- 每次向用户提交 UI 设计图——设计稿、原型、用于交付/验收的页面截图——必须**同时提供叠层区域标注图**（编号色块 + 图例对照），不得只给裸图。
- **标注以功能模块为单位，不只按视觉分区**：区域边界应与功能模块对齐（如顶栏、侧边导航、筛选栏、列表区、操作按钮组、状态栏各占一个编号），让用户能直接说「改模块 3」来指明修改目标；纯粹装饰性的视觉分区不单独编号。
- **图例必须三方映射**：每个编号同时给出「区域名称 + 功能模块说明 + 对应实现文件/组件（原型阶段可写计划归属）」，使标注既是设计交流语言，也能直接定位到代码。
- **优先复用项目既有编号体系**（如 `specs/design/区域标注/` 的标注图 + `区域标注图例.md` + 生成脚本）；新页面/新视图首次出图时按「页面首字母 + 序号」新建编号并**登记进图例表**。
- UI 结构变更导致区域边界变化时：用最新截图/原型重跑生成脚本，同步更新标注图与图例表。
- 标注图必须当即在会话中渲染展示（`read` 渲染 png），不得只落盘；**渲染时同步展示图例表**，方便用户当场按编号提意见。
## 3. 展示与确认记录
- 原型与标注图**当即主动在会话中渲染/说明给用户看**，不能只落盘、不能用文字描述替代（同源纪律：磁盘留证 + 会话展示双轨并行，两件事都做）；展示须覆盖 §2.1 声明的全部目标视口（桌面/移动各至少一组），多端适配是设计定稿确认项的一部分。
- 同时给出设计要点与影响面：涉及模块/文件、预期行为、**明确不做什么**。
- 有意调整？先改设计图再确认；定稿后归档进规格目录，方可进入技术设计。
## 4. 实现对比（闭环）

- 开发完成后、标记验收完成前，产出**设计稿与实现的对比报告**（如项目有 `tools/design-compare.ps1` 则运行之），归档进规格目录；缺对比证据不得标记验收完成。
- 对比发现的偏差走 bugfix-workflow（行为与设计不符）或 feature-evolution（设计需调整），不现场顺手改。
## 5. 边界

- 只管"长什么样、怎么交互"；数据模型、API 契约、代码实现是下一阶段的事，不在设计稿中展开。
- 设计稿不替代 TDD、黑盒测试或真实浏览器验收（feature-blackbox-test）。
