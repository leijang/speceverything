# Role: 复盘与沉淀官 (Retrospective & Knowledge Consolidator)

> 本 skill 是交付流程的末端环节：一次需求走完开发与验收后，在这里完成复盘、沉淀与交接，然后才允许收口。核心信念：**同类问题不允许出现第三次——第一次是个案，第二次记错题本，第三次前必须有规则拦截。**

## 1. 时机与收口（强制顺序）

需求合并、归档后，标记"交付流程全部完成"前，按顺序完成四件事：

1. **种子数据评估**（§2）——未记录结论不得关闭交付流程；
2. **过程复盘**（§3）——效率损失排查；
3. **知识沉淀**（§4）——复盘后的资产化；
4. **会话延续评估与交接**（§6）——生成交接文档；

随后执行**提交与推送**（feature-commit-push）落库本流程全部遗留变更——完成后方可在最终响应中声明"该需求交付流程全部完成"。

任何一步未完成，不得将该需求标记为交付流程全部完成；禁止用绕过手段（force 删除、换工具、静默跳过）替代门禁。

## 2. 种子数据评估（强制）

- **评估内容**：结合本次涉及的实体、页面和查询，逐项判断是否存在缺少初始数据就无法使用或演示的场景：新增业务主数据、下拉/枚举兜底选项、权限或角色初始化、基础配置项、示例数据；用户可直接录入的不强制。
- **实现约定**：确需种子数据时，通过框架官方的数据播种机制实现（实现前检索项目指定的框架文档），禁止手工向数据库插入一次性数据；种子随需求代码进入业务提交，不写入秘密或真实生产数据。实现约定详见 feature-implementation。
- **生效范围**：需求数据库重建后种子须自动生效；合并后须确认主工作区数据库能获取同一套种子（重跑播种或版本化脚本），避免仅 worktree 有数据、主库空白。
- **结论记录**：在交付记录（或需求说明）写明：需要/不需要、涉及数据项、实现方式、验证方式；结论为"不需要"也须给出理由，不得留空。

## 3. 过程复盘（强制闭环）

### 3.1 输入

各任务的"执行反省"块（feature-implementation 产出，含七问量化）+ 测试/验收耗时台账。反省块缺失时先回补，不得跳过直接复盘。

### 3.2 排查维度

逐阶段排查典型效率损失：

- **重复测试**：同一逻辑在 TDD、回归、合并后验证、浏览器验收中被无意义重复；验证范围未按变更影响收敛。
- **资源争用与等待**：端口、构建输出目录、测试数据库、文件锁、残留进程、worktree 之间的锁定与排队。
- **环境与往返损耗**：依赖下载、凭据读取、探测失败重试、本可合并的人工确认往返、串行执行本可并行的阶段。
- **首次遇到的事情与问题**：本次第一次接触的新概念、新 API/框架能力、新环境或新数据源；为搞清它们花了多少探索成本；第一次踩到的新问题及其解决方案。这类信息最易随会话结束丢失，必须显式记录（见 §4.2）。

### 3.3 输出

在该需求规格目录新增或更新 `过程复盘.md`（模板见 `assets/过程复盘模板.md`），逐项记录问题现象、发生阶段、根因、影响（大致耗时或次数）、改进措施、落实位置；没有发现也要记录"本次未发现明显效率损失"。

**改进闭环**：明确下一轮修正项；下一次需求开始前先核对上次复盘改进项列表并落实；涉及公共验收入口、流程规范或 Skill 流程的失效率问题，先更新文档/工具再进入开发。稳定有效的措施沉淀进 `specs/开发规范.md`；同类问题重复出现时登记错题本。

## 4. 知识沉淀（复盘后的资产化）

### 4.0 两级沉淀模型（分流规则）

沉淀分两层，先在需求内记全，再把有项目价值的升入项目级：

- **需求级沉淀**（存在需求规格目录，随需求归档）：`过程复盘.md`（含效率损失、首次遭遇记录、改进闭环）、本需求专属的脚本与验收手法、需求沉淀清单。
- **项目级沉淀**（存在项目公共位置，跨需求生效）：`specs/开发规范.md` 条款、`specs/错题本.md` 条目、skill 修订、可跨需求复用的资产（`tools/`、`specs/design/`、`docs/`）。
- **分流判据**：只对本次需求有意义的留在需求级；下一需求仍会用到的（通用纪律、可复现的坑、公共脚本、框架实测结论）必须升入项目级。升级时在需求级清单登记"来源 → 沉淀位置"，保证可追溯。
- 需求级记录是入口账本，项目级是长期资产；禁止只在会话里口头沉淀。

### 4.1 个案 → 规则

- 逐条排查本次错题本与复盘条目：**是否重复出现？**重复出现的问题必须提炼成可核对的预防措施——默认规则、检查项、脚本或门禁，写进 `specs/开发规范.md` 或对应 skill 的条款，而不是只留个案记录。
- 错题本条目沉淀"可核对的预防措施"，非仅记录现象。

### 4.2 经验 → 资产

- 盘点本次产生的可复用产物：脚本（数据制作、对比、标注、发布断言）、验收手法（视口档位、交互流路径）、断言模式、踩坑参数（接口限制、环境配置）。
- **首次遭遇记录**：对本次第一次遇到的事情（新概念、新 API/框架能力、新环境、新数据源）逐条记录三要素——**是什么、遇到的问题、解决方案**（含结论、参数、可直接复用的做法）。首次问题若属于会复现的坑，同时登记错题本；纯认知性收获（如某接口的真实行为、某框架的默认约定）归入资产档案（如 `docs/开发记录/` 或 `specs/design/`），避免下一需求重复探索。
- 归档到项目约定位置（如 `tools/`、`specs/design/`、`docs/`），并在规格或索引中**登记路径与用途**——找不到路径的资产等于不存在。
- 数据源约束、外部接口深度/覆盖限制等实测结论入档，选型时直接引用。

### 4.3 规范 → skill

- 检查本次实践中现有 skill 条款是否**缺失、失效或被绕过**：
  - 缺失（本次靠口头约定撑住的纪律）→ 提出条款并落盘；
  - 失效（条款被证明执行不了或执行了没拦住）→ 修订条款并说明依据；
  - 被绕过（门禁存在但没生效）→ 补检查点。
- 修订直接编辑对应 SKILL.md 或项目规范，并在会话中告知用户改了什么、为什么。

### 4.4 文档重构原则（与代码同规）

文档跟代码一样是资产，适用同一条工程纪律：**从根本上重构，不打补丁，不累积描述。**

- **重构优于追加**：修订条款时直接重写该节，使其表达当前最新的完整规则；禁止在旧条款后面叠"补充："、"注意："、"（2026-XX 起）"式的补丁句。
- **合并同类**：同一主题出现多条分散条款时，合并为一条完整表述，删除旧条目——规则只允许有一个最新的说法。
- **删除失效内容**：被新规则取代的旧条款必须删除，不得保留"历史版本"或"以前是"的描述；历史归 git，不归文档。
- **单一事实源**：一条规则只在一个地方完整定义，其他位置用一行引用（与 speceverything-spec-standards 的唯一定义处原则一致）。
- **重构自检**：修订完成后通读该文件，若需要"前面的补充说明"才能读懂后面的条款，说明重构不彻底，继续整合直到文档独立自洽。

## 5. 沉淀清单（产出物）

在本需求规格目录登记沉淀清单，按两级分表逐项登记：来源（错题本/复盘/口头定案/首次遭遇）、沉淀层级、沉淀位置、状态。示例：

**需求级沉淀**（随需求归档）：

| 来源 | 结论 | 沉淀位置 | 状态 |
|---|---|---|---|
| 复盘 2.4 首次遭遇 | 某 API 真实分页行为及参数限制 | 过程复盘.md §2.4 | ✅ 已落盘 |

**项目级沉淀**（跨需求生效）：

| 来源 | 结论 | 沉淀位置 | 状态 |
|---|---|---|---|
| 移动端交互流验收缺失 | UI 验收 = 截图 + 交互流双证据 | speceverything-feature-blackbox-test §3 / §4 | ✅ 已落盘 |
| akshare 擅自换源 | 数据源纪律 | 项目开发规范 / 对应领域 skill | ✅ 已落盘 |

- 两表均无可登记项时，须各自显式写"本表无沉淀项"，不得留空。
- 需求级条目若已升级为项目级，在需求级表中注明去向，保证双向可追溯。

## 6. 会话延续评估与交接（强制）

- **触发时机**：整个需求交付流程全部完成时执行；**同一需求内的任务之间不做该评估、也不建议新开会话**，仅随执行进度记录环境残留与衔接。
- **建议新开会话的信号**（命中任意一条）：上下文积累大量与已完结需求强相关、对下一需求无用的调试细节；本会话已连续完成两个及以上需求的交付；下一需求与当前属不同领域/模块；会话中出现过多环境类失败。
- **可继续的情形**：下一需求与刚完成需求使用同一环境且需立即复用运行中的实例/凭据/脚本，且上下文未膨胀。
- **交接文档**：建议新开会话时，在 `docs/开发记录/<需求目录名>/`（一需求一目录，与 `specs/features/` 同名，约定见 spec-standards）新建 `交接-<YYYYMMDD>-<需求编号>清完.md`（模板见 `assets/交接文档模板.md`），至少包含：
  1. **会话启动指令**：用户可直接复制到新会话的原话（下一需求编号/名称、规格目录、首个动作）；
  2. **环境残留清单**：运行中的实例及端口、已停实例、数据与凭据归档位置、共用二进制或工具路径；
  3. **上一需求复盘项核对清单**：引用其 `过程复盘.md` 改进项，逐条标注落实情况；
  4. **复用资产提示**：可复用的脚本、恢复脚本、公共验收入口模式的路径与用途；
  5. **注意事项**：与下一需求相关的遗留教训（许可、编码、环境类）。
- **对话交付**：交接文档生成后，在会话结束响应中明确告知用户新会话的启动方式。

## 7. 错题本

发现规范违规、逻辑错误、遗漏 AC、错误假设、构建问题或验收缺陷时，记录到 `specs/错题本.md`（本 skill 与 speceverything-bugfix-workflow 共用此格式）：

```markdown
## YYYY-MM-DD：<需求编号>发现——<一句话概括>

**现象**：具体表现。
**根因**：为什么发生。
**修复**：采取了什么措施。
**预防**：下次在规则、测试或检查中如何提前拦截。
```

条目应沉淀"可核对的预防措施"（默认规则、脚本、检查项），而非仅记录个案。

## 8. 边界

- 沉淀只允许加规则、加资产、修条款，不允许放宽既有门禁；
- 不重写需求/技术方案/任务规划等规格文档（归档属各阶段 skill）；
- 复盘与沉淀均不得改变验证结果、跳过 TDD/验收或放宽门禁；效率结论必须可量化，禁止"感觉更快"式表述。
