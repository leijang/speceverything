## 目标
你的目标是解决“先做什么，后做什么”的问题。基于《产品概述》中的核心板块，分析模块间的依赖关系，制定一份合理的**开发路线图 (Development Roadmap)**，即 `specs/开发路线图.md`。

## 边界守卫 (Guardrails) - CRITICAL
请严格遵守通用边界守卫规则：[specs/GUARDRAILS.md](specs/GUARDRAILS.md)

## 背景
新手开发者往往容易陷入“迷茫”，不知道项目初始化完成后该从哪个功能开始下手。你需要提供一个清晰的导航图。

## 输入
*   `specs/产品概述.md` (提取核心板块和业务流程)
*   `specs/项目结构.md` (参考模块划分)
*   **开发团队规模** (人数；用户未提供时，必须先询问确认，禁止臆测)

## 关键概念定义
*   **需求目录 (Requirements Catalog)**：每个里程碑下的方向性需求清单。它不是 feature 级的《需求说明》，而是"这个里程碑要交付哪些需求"的方向性指导，为后续逐个需求走 feature 流程提供入口。
*   **并行任务划分 (Parallel Task Split)**：在里程碑内，根据开发人数把需求拆成可同时进行的任务，明确"谁 × 哪个任务"。

## 工作流程
1.  **依赖分析 (Dependency Analysis)**：
    *   识别哪些模块是"地基"？（通常是：用户/认证、基础配置、公共组件）。
    *   识别哪些模块是"核心业务"？（必须优先完成，否则产品无价值）。
    *   识别哪些模块是"锦上添花"？（可以延后）。

2.  **里程碑规划 (Milestone Planning)**：
    *   **Milestone 1: MVP (最小可行性产品)** - 包含最核心的业务闭环（如：地基 + 核心业务）。
    *   **Milestone 2: 完整版 (Full Features)** - 包含所有主要功能。
    *   **Milestone 3: 增强版 (Enhancement)** - 包含非功能性优化、统计报表等。

3.  **需求目录制定 (Requirements Catalog)**：
    *   为每个里程碑列出其包含的全部需求，形成方向性指导的需求目录。
    *   每条需求给出：名称、一句话范围说明、前置依赖；不预占 F00X 编号（编号在需求正式创建时按 speceverything-spec-standards §4 分配登记，避免与他需求冲突）。
    *   需求目录是方向性的：只界定"做什么、什么顺序"，不深入 AC / 技术方案（那是 feature 阶段的事）。

4.  **团队评估与并行任务划分 (Team Assessment & Parallel Splitting)**：
    *   **确认开发人数**：向用户确认有几个人同时开发；人数变化时必须重新划分。
    *   **划分原则**：
        *   尽量让**多个人协作开发同一个模块**（模块内按任务拆给不同人），避免一人独占整模块形成瓶颈。
        *   尽量让**一个任务由多人并行推进**（按层次拆分时前后端/数据层可分头进行）。
        *   任务划分维度二选一或混用：
            *   **按架构层次划分**：同一模块拆成 数据层 / 服务层 / 接口层 / UI 层，分给不同人并行。
            *   **按模块划分**：不同模块分给不同人，模块内部再按层次拆。
    *   **约束检查**：划分后逐项核对——每个任务都有明确负责人；有依赖的任务排了先后顺序；无依赖的任务尽量落在同一时间段并行；单人负责的任务数大体均衡。

5.  **排序与指令 (Sorting & Commands)**：
    *   为每个里程碑内的功能模块建议开发顺序。
    *   为每个任务生成具体的提示词 (例如：`"开发[具体模块名]的[任务名]..."`)，让 roadmap 具有可执行性。

6.  **进度检测 (Progress Detection)**：
    *   **扫描现有文件**：
        *   若 `specs/项目结构.md`（structure 产出）定义的模块目录已存在 -> 标记对应模块开发任务为 `[x]`；模块位置约定不明时向用户确认，不硬编码猜测。

7.  **生成文档**：输出符合模板的 Markdown 文档，**根据检测结果预先勾选已完成的任务**。

8.  **最终交付**：保存到 `specs/开发路线图.md`。
