# Role: 规格管理员 (Spec Custodian)

> 本 skill 是 `specs/` 规格体系的唯一定义处。核心信念：**规格是交付的唯一事实源——目录可寻、编号唯一、状态如实、链路可追溯。**

## 1. 规格目录结构

- 每个需求独立目录：`specs/features/XXX-功能名称-YYYYMMDD/`。
  - `XXX` 为三位递增编号（F001、F002…），**不复用**，已取消的需求编号同样不回收。
  - 目录名主题用中文，编号与日期用 ASCII。
- 主文档为该目录下 `需求说明.md`。

## 2. 各阶段文档命名（同目录内）

| 文档 | 产出方 |
|---|---|
| `需求说明.md` | feature-requirements-clarification |
| `UI设计稿/` | feature-hifi-design |
| `技术方案.md` | feature-tech-design |
| `任务规划.md` | feature-task-planning |
| `变更任务_CR-XXX-变更题目.md` | feature-evolution |
| `编码复核.md` | feature-code-review |
| `验收截图/` | feature-blackbox-test |
| `过程复盘.md` | feature-summary |
| `specs/features/index.md` | 所有产出方（新建或状态变更时同步） |

禁止扁平命名（如 `specs/features/{功能名}_技术方案.md`）——同需求的所有文档必须聚在其规格目录内。

## 3. 索引状态（index.md）

至少区分：规划中、需求已确认、设计已确认、开发中、已实现/待验收、已完成、修复中、已取消。

- 状态必须反映**真实证据**，不以代码存在代替验收完成。
- 新建规格、状态变更、CR 登记时必须同步更新 `specs/features/index.md`。

## 4. 编号体系

| 编号 | 含义 | 递增起点 |
|---|---|---|
| `F00X` | 需求（规格目录编号） | F001 |
| `CR-XXX` | 变更任务（feature-evolution 登记） | CR-001 |
| `BUG-XXX` | 缺陷（bugfix-workflow 登记） | BUG-001 |
| `Task-XX` | 任务（任务规划内） | Task-01 |
| `AC-XXX` | 验收标准（需求说明内） | AC-001 |

编号在各自体系内全局递增、不复用；AC 编号在单个需求内递增。

## 4.1 分支与 worktree 命名规范

worktree/分支命名属于编号体系的延伸——所有命名必须能回溯到 §4 的编号。格式与语言纪律统一由本节定义，各流程 skill 引用执行：

| 对象 | 规范 | 示例 |
|---|---|---|
| worktree（需求） | `codex/<需求编号>-<中文主题>`，分支名 = worktree 目录名 | `codex/F005-实时题包` |
| worktree（变更单元） | `codex/<需求编号>-CR<XXX>-<中文主题>` | `codex/F005-CR009-实时题包` |
| worktree（任务单元） | `codex/<需求编号>-Task<XX>-<中文主题>` | `codex/F005-Task03-实时题包` |
| 里程碑分支 | `milestone/<yyyymmdd>-<中文主题>` | `milestone/20261124-实时题包` |

- **语言纪律**：日期/编号/前缀用 ASCII（`milestone/`、`codex/`、`yyyymmdd`、`CR-XXX`），主题一律**中文**——不在同一分支名内中英混用主题。
- **禁止光秃编号**：命名中必须带主题，`codex/F005` 这类裸编号不合法。
- 创建/复用/清理的**流程规则**（占用检查、粒度升级、生命周期）不在本节，见 feature-release-deploy §2。

## 5. 编号交流规则（强制）

向用户描述规格中登记的任何编号时，必须**「编号 + 名称」**同时给出：

- ✅ `CR-003（按题包按需拉取）`
- ❌ `CR-003 已完成`

首次出现给全名，同一回复内再次出现可只带编号。

## 6. 何时必须建/更新规格

- **新建**：新增功能、修改核心行为/主流程/状态机/权限/外部交互、跨模块跨文件可能改变行为的重构、需要多轮对齐的需求。
- **更新**：需求变更走 feature-evolution 的 CR 流程；行为与既定规格不符走 bugfix-workflow，两者不混用。
- **不需要**：不改变任何已登记行为的内容（如纯注释、纯格式调整）不强制新建规格，但仍须核对是否影响既有文档描述。

## 7. AC 与追溯链路

- AC 质量标准（编号、Given-When-Then、三类场景缺一不可）由 feature-requirements-clarification 定义，本规范不重复。
- **贯穿链路**：技术方案、任务规划、测试和验收必须能按 AC 编号追溯；不允许出现"已覆盖"但找不到实现、任务或证据。

## 8. 底线规则

- 不在规格目录体系外保存需求/方案/任务类文档；散落的旧扁平文件应迁入对应需求目录。
- 编号不复用；状态不虚报；索引不滞后。
- 本规范与任何阶段 skill 冲突时，以本规范为准（本 skill 是唯一定义处）。

## 9. 全局架构资产（specs/design/架构.md）

- **位置与形态**：`specs/design/架构.md`——全局系统架构图（Mermaid，分层/模块/数据流/外部依赖）+ 各模块一句话职责 + 模块间依赖方向说明。
- **初始建立**：项目初始化（project-structure 完成目录结构后）建立；若项目已存在但从未建立，在**下一次技术设计**时由 feature-tech-design 顺带建立，不得再拖延。
- **同步义务**：任何需求的技术设计若改变全局结构（新增模块、新增外部依赖、数据流变化、模块职责变更），必须在同一设计内同步更新全局图，并在文末变更记录登记需求编号。
- **漂移检查**：发现全局图与实际实现不符时，当场修图或修码（与 feature-tech-design 的衔接条款一致），不允许"图是旧的"持续存在。

## 10. 开发记录目录（docs/开发记录/）

- **一需求一目录**：`docs/开发记录/<需求目录名>/`，目录名与 `specs/features/` 下对应需求目录**完全同名**（`XXX-功能名称-YYYYMMDD`）。
- 归入该目录的产物：阶段完成报告（feature-implementation）、交接文档（feature-summary）。
- 该需求的工作全部结束（feature-commit-push 完成落库）后，目录内容随需求一并归档，不再追加散落在 `docs/开发记录/` 根层的文件。
