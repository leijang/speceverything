# 错题本

> 条目格式定义处：speceverything-feature-summary 第 7 节。每条沉淀「可核对的预防措施」，非仅个案记录。

## 2026-11-27：F001 发现——被跟踪的生成物含易变字段，使一切「干净基线」门禁永久失效（BUG-001，两腿）

**现象**：变异自证 YJ-01 首跑被基线门禁拦截（`M tools/skill-audit-report.md`）；修复时间戳后 harness 又把自身报告误判为「DIRTY AFTER RESTORE」。
**根因**：报告是被 git 跟踪的生成物且含分钟级时间戳行——任何审计运行都把工作区弄脏；第二腿是 harness 的全局脏检查不区分「自身可再生产物」与「植入残留」。
**修复**：删时间戳行，报告内容成为库状态纯函数（证据时间归 git 历史）；基线与还原核验排除 `skill-audit-report.md`（逐文件核验仍精确把关植入残留）。
**预防**：生成物入 git 跟踪必须内容确定性（无时间戳/无随机序）；凡「干净基线」类门禁必须把自身输出物显式排除。可核对拦截：`regression-guard.Tests.ps1` 确定性测试（无易变行 + 两次运行逐字节一致）。

## 2026-11-27：F001 发现——PS 5.1 对无 BOM 的 UTF-8 .ps1 按 ANSI 解析，中文字面量静默劣化

**现象**：Pester 测试脚本解析报错；若发生在含中文正则的脚本里则更危险——正则静默变成乱码、永不命中。
**根因**：Windows PowerShell 5.1 官方编码行为：无 BOM 即按系统代码页解析。
**修复**：全部含 CJK 的 .ps1 重存 UTF-8 BOM；脚本头注声明该要求。
**预防**：任何 .ps1 含非 ASCII 字面量，保存前核对 UTF-8 BOM。可核对拦截：`Select-String -Pattern '必须|禁止' tools\*.ps1` 命中而文件无 BOM 即为违例（纳入提交前审计仪式）。

## 2026-11-27：F001 发现——PS 5.1 在 EAP=Stop 下把原生命令 stderr（经 2>$null 重定向）升级为终止异常

**现象**：`git checkout` 遇 pathspec 错误时函数抛终止异常而非返回失败清单，AC-004 判定路径被挡。
**根因**：官方行为：stderr 行经重定向包装为 ErrorRecord，EAP=Stop 使其终止。
**修复**：函数内局部 `$ErrorActionPreference='Continue'` + finally 恢复，代码注释留痕。
**预防**：EAP=Stop 脚本内调用可能写 stderr 的原生命令时，局部降级并在注释说明原因；测试必须覆盖该路径（mutation-engine AC-004 用例）。

## 2026-11-27：F001 发现——规格文档内裸「§N」自指引用被审计解析为断链，字面「spec 斜杠字样」被计为路径命中

**现象**：F001 自身规格文档若原样入库，审计将报 BROKEN 引用与 spec 斜杠字样 命中，门禁永久红。
**根因**：审计的 §N 解析规则=「同行前面的 skill 名，无则自指本文档」；规格文档自身无对应编号节即断链；「spec 斜杠字样」字样无论语义都计入单数路径检查。
**修复**：规格文档引用一律用「第 N 节」中文表述（或「文档名.md 第 N 节」）；缺陷类别描述写「spec 单数路径」不带斜杠。
**预防**：任何 .md 文档入库提交前先跑 `tools/skill-audit.ps1`——本轮靠该仪式当场拦住（7 处文件 14 处命中全部修复后才 CLEAN）。

## 2026-11-27：F001 发现——仓库无行尾归一化约定，尺寸表 chars 列跨 checkout 漂移

**现象**：同一库内容，worktree（CRLF）chars=5831、主仓原始检出（LF）chars=5631；golden 逐字节对比因此跨 checkout 不稳定。
**根因**：无 .gitattributes；原始检出与 autocrlf 新检出行尾不一致。
**修复**：黄金对比行尾归一化 + 契约区收窄（第 4 节 chars 列除外，预算指标 token 列行尾稳定、由退出码门禁把关）。
**预防**：待用户决策——引入 `.gitattributes`（`* text=auto` + renormalize）为跨全仓一次性变更；在此之前，任何逐字节对比必须先归一化行尾。

## 2026-11-27：深化 D4 发现——PS 5.1 捕获原生命令输出时按控制台代码页解码，中文必乱码（编码陷阱第三现）

**现象**：`git log --format=%s` 等含中文的原生命令输出，被 PS 捕获后呈乱码——本会话多次实证（git log 显示乱码；若审计走 PS 侧捕获即判定被污染）。
**根因**：PS 5.1 用 `[Console]::OutputEncoding`（本机 GBK/936）解码原生命令的 UTF-8 stdout；与条目 2（输入侧 ANSI 解析）、条目 3（stderr 升级终止）同族，是平台编码陷阱的第三个形态。
**修复**：审计第 9 节采用 **git 侧匹配**（`--invert-grep -E`）——判定在 git 进程内完成（UTF-8 干净），报告行只落 ASCII 哈希，PS 捕获层被完全绕开。
**预防**：需要读取原生命令的**中文输出内容**时，优先让该命令自己完成判定/过滤（git --grep、--format 计数等）；确需 PS 侧捕获文本时必须先设 `[Console]::OutputEncoding=UTF8`（重定向句柄下可能抛异常，需 try/catch 兜底字节级读取）。可核对拦截：第 9 节报告行全 ASCII，出现乱码即代表本预防被绕过。

## 2026-11-27：标准采纳时发现——审计脚本各节行列表变量同名遮蔽，后节初始化清空前节已收报告行

**现象**：第 10 节（Agent Skills 合规）沿用 `$specRows` 变量名，其初始化在第 3 节收集之后执行，把 第 3 节 已收好的报告行清空——退出码（独立计数器）正确报 1，但报告行消失，变异捕获判定器据此判 T1 UNCAPTURED。
**根因**：单脚本内多节各自维护行列表，新增节复用了既有节变量名；计数器与行列表分离使退出码掩盖了报告行完整性缺陷。
**修复**：各节行列表唯一命名（refRows/assetRows/specRows/dupRows/bomRows/idxRows/cmRows/specViolRows），第 10 节 改名 `$specViolRows`。
**预防**：审计脚本新增检查节时行列表命名必须带节语义前缀；可核对拦截=变异自证必跑（本案即由 T1 的 第 3 节 行捕获判定当场暴露——报告行完整性与检查逻辑同在变异门禁守备范围）。

## 2026-11-27：部署时发现——全局注册的 skill 是静态拷贝，仓库深化两轮未部署，注册层静默漂移

**现象**：用户要求部署时对比发现全局目录（`~/.config/opencode/skills/`）与仓库不一致：23 个 SKILL.md 落后，涵盖上轮审计修复（blackbox 测试用例先行、project-requirements 分流句等）与本轮深化（CR 路由、一致性自检、二次合并、D2 删除、mysql 引号）两轮内容。
**根因**：部署是手动拷贝、无触发机制——「仓库已修」对全局注册层不自动成立；且注册层描述与会话系统提示绑定，漂移不可见（直到明确对比）。
**修复**：全量同步 64 个文件（23 个更新 + 补 mudules/README.md），哈希复验零不一致、零孤儿；harness 热加载确认生效。
**预防**：每轮改动 skill 库的会话收尾时，跑一次仓库→全局的哈希对比（本会话已验证的一行式：两侧 `Get-ChildItem -Recurse -File` 逐文件 `Get-FileHash` 比对），差异非零即部署；或把全局目录改为指向仓库的链接。
